# What a pick does, and where

A pick changes more than the pick log.

## The chain

Every pick, however it is made, goes through `TurnsService.pickCard` in `api/src/drafts/turns.service.ts`: by hand (`pick`), from a queue (`cascade`), by a bot (`botPick`, which calls `takeTurn`), or when a player sets their queue to queue picking on their own turn (`setQueuePicking`, which checks the cards the player confirmed against `queuePicksBeforeAnotherPlayerPicks` in `engine/src/queue-picks.ts`, then runs the cascade). A turn reads the draft once under the lock, as the `TurnRead` in `api/src/drafts/turn-read.ts` (`readTurn`): players by seat (each a `TurnPlayer`), their queues (each the engine's `SeatQueue` from `engine/src/queue.ts`, holding its queued rows, its steal behavior and whether it is queue paused), the pool, and the cards picked so far. `pickCard` checks each pick against it and updates it as it writes, and the cascade starts from it, so no pick reads the draft again. A pick import (`api/src/drafts/pick-import.service.ts`) creates its picks in bulk and then records their effects on plans the same way. After creating the `Pick` row, `pickCard` hands the made pick, as the `MadePick` shape in `api/src/drafts/draft-shapes.ts`, to one helper per thing a pick touches:

- `api/src/drafts/plan-picks.ts`: what the pick does to players' plans, which is only to put the pick in its player's plan on the deck board it lands on (`recordPlanEffects`; `planPicks` does it for a pick import), and how an undo takes it out again (`restorePlans`). A plan holds only picks and basic lands, so no other plan changes.
- `api/src/drafts/queue-effects.ts`: what the pick does to players' queues (`recordQueueEffects` persists what the engine works out, using the queued positions the turn holds, including what each loss did to its queue, and returns each queue state as it now is), and how an undo puts it back (`restoreQueues`, which also sets queue picking again a queue that pick paused).

The engine decides every effect; the api only persists it. `queuesAfterPick` in `engine/src/queue.ts` works out one pick's effects, through `engine/src/copies.ts` for the copy rule: `ownPickCopy` for the queued copy in the picker's own queue that the pick accounts for, `swapOrLose` for every other seat's; and `queueAfterUndo` in `engine/src/queue.ts` is where an undo puts taken-out queued cards back.

Each queued copy sits on a deck board, which the engine's `SeatQueue` carries on each of its queued copies (`QueuedCopy`, a card and its `board`) and the api's `QueuedCard` and `TakenOutQueuedCard` rows as `board`. `queuesAfterPick` keeps a swapped-in copy on the stolen copy's board, says in the picker's queue, as `landsOn`, which board the pick lands on in their deck (the board of the queued copy `ownPickCopy` names, or the mainboard), and `recordPlanEffects` puts a new pick there; `queueAfterUndo` puts each taken-out card back on the board it had. A pick import's effects, landing boards included, come from `pickImportEffects` in `engine/src/pick-import.ts`, which applies its picks to the queues in turn, as the cascade does. `nextQueuedPick` in `engine/src/queue.ts` is the one step of every queued pick: the first available card of the queue whose turn it is, unless queue paused, and what it does to every queue; both the cascade and `queuePicksBeforeAnotherPlayerPicks` repeat it. The cascade, `engine/src/cascade.ts`, takes one `SeatQueue` per seat, stops at a seat whose queue is empty or queue paused, and returns each pick with its effects on every queue, landing board included, so for a cascade pick `pickCard` passes them straight to the `record…` halves; a by-hand pick and a bot's pick work out their one pick's effects first, and a pick import its picks' effects, from the state they hold, then pass them to the same halves. `recordQueueEffects` and `recordPlanEffects` are the only writers of a pick's effects on queues and plans, for every kind of pick. Queued cards a pick takes out (`TakenOutQueuedCard` in `api/prisma/schema.prisma`) are kept against the pick, each with its board, so that `TurnsService.undo` can put them back, then deleted with the pick.

Adding a new effect of a pick means: a pure engine function with its own spec, which `cascade` also returns for each pick, a helper beside the two above that `pickCard` and the pick import call, and a restore that `undo` calls before deleting the pick. A turn's state must change as the database does, so a helper that writes returns what it changed, and `pickCard` puts that back in the state. The pick import applies effects in pick order, so `planPicks` builds "picked so far" one pick at a time. Every effect follows "A change a draft shows bumps its version and pushes it" in `CODING_STANDARDS.md`: bump in the pick's transaction, push after commit, and log a failed push rather than fail the pick.

## The web side

`web/src/app/drafts/draft-store.ts`, the draft-scoped service the draft page provides, re-reads the pick log and the signed-in player's queue and plan whenever the draft's `version` changes, which every pick, undo and lifecycle change bumps. A tab that must learn about a pick's effect injects it and needs nothing more than its read there; the Queue and Deck tabs are the models. A change to the player's queue or deck (the store's plan) that no one else sees, such as pausing the queue, moving a queued copy to another deck board (`PUT drafts/:id/queue/:poolCardId/board`) or moving a card to the sideboard, bumps no version, so the store also re-reads both whenever the window gains focus or is shown again, which is how a player's second window catches up; while their deck locks at Start it re-reads the tournament then too, as the deck decides whether they may mark themselves ready.

## Specs

- Engine: `engine/src/*.spec.ts`, pure, with a hand-made `pool` map.
- API: `api/src/drafts/specs/*.spec.ts` through supertest, built on `harness.ts` there (`readyDraft`, `readyDraftWithCopies`, `readyDraftWithCopiesOutOfIdOrder` for a test whose result depends on which copy the copy rule takes, `pick`, `undo`, `enqueue`, `queueInLobby` for a queue already filled in the lobby, which the api no longer lets a player add to, `importPicks`, `addBot`, `setQueuePaused` and `setQueuePicking` to pause a queue or set it picking, `queuePaused` to read which it is, `useBob` to sign Bob in as `bobCookie` before each spec, `useAnnouncements` to do that and register a webhook as `webhookId`, `readyDraftOnWebhook` for a draft of Alice and Bob announcing on it, and `posted` for what was posted once the draft's announcements have settled), which is built on `api/src/testing/app.ts` (the app with every outbound client faked, and `signIn`). Read the harness and one `it` block of the nearest spec for conventions; the harness doc comments list the gotchas.
- API races: `api/src/drafts/specs/*.race.spec.ts`, a vitest project of its own on a real Postgres, built on `race-harness.ts` there (`describeRaces`, which signs Bob in through the harness's `useBob`, `race`, and `raceLastCommitFirst`, which lets the request that reached its COMMIT last commit first, so the other commits only after it has answered, and `raceBehindLongCommit`, which holds a pick's COMMIT past Prisma's 5 s default transaction timeout while a change waits on its lock). Each races two requests whose order a row lock decides (the draft row lock, `lockPlayer`, which queue and deck changes take through `DraftLock.forPlayer` in `api/src/drafts/draft-lock.ts` and so run with its locked change timeout, or the user's row, which a sign-in locks and a Lobby join or draft creation share-locks first through `shareLockUser`), and fails if that lock is removed. A new change that takes one of those locks gets a race there against the changes it contends with: for the draft row or `lockPlayer`, picks, undo or cascades; for the user's row, a sign-in, a Lobby join or a draft creation. Skipped unless `RACE_DATABASE_URL` names a local server (CI's postgres container); never point it at `DATABASE_URL`'s.
- Web: `web/src/app/drafts/specs/*.spec.ts` through the HTTP stand-in, built on `harness.ts` there (`openDraft`, `flushPlan`, `flushQueue`, `button`) and `pool-tab-harness.ts` (`openDetail`).
