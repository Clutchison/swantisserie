# What a pick does, and where

A pick changes more than the pick log.

## The chain

Every pick, however it is made, goes through `TurnsService.pickCard` in `api/src/drafts/turns.service.ts`: by hand (`pick`), from a queue (`cascade`), by a bot (`botPick`, which calls `takeTurn`), or when a player sets their queue to queue picking on their own turn (`setQueuePicking`, which checks the cards the player confirmed against `queuePicksBeforeTurnPasses` in `engine/src/queue-picks.ts`, then runs the cascade). A turn reads the draft once under the lock, as the `TurnState` in `api/src/drafts/turn-state.ts` (`readTurnState`): players by seat (each a `TurnPlayer`), their queues (each the engine's `SeatQueue` from `engine/src/queue.ts`, holding its queued rows, its steal behavior and whether it is queue paused) and plans, the pool, and the cards picked so far. `pickCard` checks each pick against it and updates it as it writes, and the cascade starts from it, so no pick reads the draft again. A pick import (`api/src/drafts/pick-import.service.ts`) creates its picks in bulk and then records their effects on plans the same way. After creating the `Pick` row, `pickCard` hands the made pick, as the `MadePick` shape in `api/src/drafts/draft-shapes.ts`, to one helper per thing a pick touches:

- `api/src/drafts/plan-picks.ts`: what the pick does to players' plans (`recordPlanEffects` persists what the engine works out, and returns the plans as they now are; `planPicks` does it for a pick import), and how an undo puts it back (`restorePlans`).
- `api/src/drafts/queue-effects.ts`: what the pick does to players' queues (`recordQueueEffects` persists what the engine works out, using the queued positions the turn holds, including what each loss did to its queue, and returns each queue state as it now is), and how an undo puts it back (`restoreQueues`, which also sets queue picking again a queue that pick paused).

The engine decides every effect; the api only persists it. `queuesAfterPick` in `engine/src/queue.ts` and `plansAfterPick` in `engine/src/plan.ts` work out one pick's effects, both through `swapOrLose` in `engine/src/copies.ts` for the copy rule, and `queueAfterUndo` in `engine/src/queue.ts` is where an undo puts taken-out queued cards back. `nextQueuedPick` there is the one step of every queued pick: the first available card of the queue whose turn it is, unless queue paused, and what it does to every queue; both the cascade and `queuePicksBeforeTurnPasses` repeat it. The cascade, `engine/src/cascade.ts`, takes one `CascadeSeat` per seat (its `SeatQueue` and its plan), stops at a seat whose queue is empty or queue paused, and returns each pick with its effects on every queue and plan, so for a cascade pick `pickCard` passes them straight to the `record…` halves; a by-hand pick, a bot's pick and a pick import work out their one pick's effects first, from the state they hold, then pass them to the same halves. `recordQueueEffects` and `recordPlanEffects` are the only writers of a pick's effects on queues and plans, for every kind of pick. Rows a pick loses or takes out (`LostPlannedCard` and `TakenOutQueuedCard` in `api/prisma/schema.prisma`) are kept against the pick so that `TurnsService.undo` can put them back, then deleted with the pick. The plan restore stays in the api: it is bookkeeping about plan boards, which the engine doesn't model.

One write to plans sits outside `recordPlanEffects`: a plan card's queue order, which `leaveQueue` in `api/src/drafts/queue-order.ts` stamps as it takes cards out of a queue. Every removal of queued cards goes through it, whether a pick takes them out (`recordQueueEffects`), the player removes them, or a pick import empties the queue. It is bookkeeping too, so it stays in the api with no engine function, and an undo leaves it alone: the cards it put back are queued again, which Queue unpicked skips, and their next departure overwrites it.

Adding a new effect of a pick means: a pure engine function with its own spec, which `cascade` also returns for each pick, a helper beside the two above that `pickCard` and the pick import call, and a restore that `undo` calls before deleting the pick. A turn's state must change as the database does, so a helper that writes returns what it changed, and `pickCard` puts that back in the state. The pick import applies effects in pick order, so `planPicks` builds "picked so far" one pick at a time.

## The web side

`web/src/app/drafts/draft-store.ts`, the draft-scoped service the draft page provides, re-reads the pick log and the signed-in player's queue and plan whenever the draft's `version` changes, which every pick, undo and lifecycle change bumps. A tab that must learn about a pick's effect injects it and needs nothing more than its read there; the Queue and Deck tabs are the models. A change to the player's queue that no one else sees, such as pausing it, bumps no version, so the store also re-reads the queue whenever the window gains focus or is shown again, which is how a player's second window catches up.

## Specs

- Engine: `engine/src/*.spec.ts`, pure, with a hand-made `pool` map.
- API: `api/src/drafts/specs/*.spec.ts` through supertest, built on `harness.ts` there (`readyDraft`, `readyDraftWithCopies`, `readyDraftWithCopiesOutOfIdOrder` for a test whose result depends on which copy the copy rule takes, `pick`, `undo`, `enqueue`, `queueInLobby` for a queue already filled in the lobby, which the api no longer lets a player add to, `importPicks`, `addBot`, `setQueuePaused` and `setQueuePicking` to pause a queue or set it picking, and `queuePaused` to read which it is), which is built on `api/src/testing/app.ts` (the app with every outbound client faked, and `signIn`). Read the harness and one `it` block of the nearest spec for conventions; the harness doc comments list the gotchas.
- API races: `api/src/drafts/specs/*.race.spec.ts`, a vitest project of its own on a real Postgres, built on `race-harness.ts` there (`describeRaces`, `race`). Each races two requests whose order the draft row lock or `lockPlayer` decides, and fails if that lock is removed. A new change that takes one of those locks against picks, undo or cascades gets a race there. Skipped unless `RACE_DATABASE_URL` names a local server (CI's postgres container); never point it at `DATABASE_URL`'s.
- Web: `web/src/app/drafts/specs/*.spec.ts` through the HTTP stand-in, built on `harness.ts` there (`openDraft`, `flushPlan`, `flushQueue`, `button`) and `pool-tab-harness.ts` (`openDetail`).
