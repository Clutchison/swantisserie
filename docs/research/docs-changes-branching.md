# Where pre-implementation decision documents land: `main` or a branch (as of 2026-11-12)

Should glossary edits, ADRs and research notes written *before* a ticket is built be committed straight to `main`, or travel on a branch and PR? Written to check two rules that disagree in our own skills: `/triage` ("Triage is finished only once every `GLOSSARY.md` and `docs/adr/` change it made is committed to `main` and pushed", `.agents/skills/triage/SKILL.md` line 49) and `/wayfinder` (research goes on an unmerged `research/<name>` branch with a pointer from the ticket, `.agents/skills/wayfinder/SKILL.md` line ~115). Setting: up to four agents in clones `a-1` to `a-4`, work lands through `ST-<n>` PRs, no branch protection on `main`.

Confidence key: **[V]** read directly in a primary source: the author's or organisation's own page, the repo's files or git history. **[C]** a secondary or community source: one voice, or a quote of a book I couldn't read directly. **[U]** my inference.

## Summary

No primary source answers this question directly: none of trunk-based development, DORA, Fowler, Write the Docs, the ADR literature or DDD singles out "decision docs written before the code" for a different landing path. What they do say pulls two ways.

**For landing decisions on `main` early (what we do now):**

- Trunk-based development and CI want small changes integrated within a day, and treat review-in-a-PR as integration friction to justify, not a default. Ship/Show/Ask lists "I updated documentation" as a typical *Ship*, straight to mainline.
- ADR guidance expects a decision to be recorded and accepted before it is built (Azure: start the log at the onset; Zimmermann: a decision is done when realization is *scheduled*; Microsoft's playbook merges an ADR to main once it is *accepted*, not once code exists).
- GitLab's "handbook first" documents a change before announcing or acting on it, aiming to merge the same day.
- For four concurrent agents, a decision on `main` is visible to every clone at the next pull; one on a branch or in another clone's working tree is invisible, so a parallel agent can contradict it.

**Against, or for a branch/PR:**

- Those same sources treat a glossary (or handbook, or user docs) as describing *what is true now*: GitLab's handbook "is what we do right now", GitLab's product docs ship with the MR that exposes a feature, and DDD's language must "always stay in sync" with the model in code. A glossary entry for unbuilt behaviour breaks that for as long as the ticket is open (here, bcb8518 renamed Paused to Frozen about 1h47m before PR #699 built it).
- Where the ADR sources tie status to merge, a *proposed* ADR lives on a PR and merges only once accepted, so the PR is the review step. Pushing straight to `main` skips both review and the Proposed state.
- Upstream Pocock skills never say "commit to `main`". The triage rule is our own addition (a00b08c, 2026-11-02). Upstream wayfinder keeps research off `main` on purpose, and upstream's research FAQ reports community advice not to keep research files in git at all.
- Many decision-only commits to the one `GLOSSARY.md` from parallel sessions are a merge-conflict surface. Upstream treats agents as good at conflicts but says to land big renames first.

**Net reading** **[U]**: the sources favour *early* landing of a decision once it is **accepted**, and favour keeping *descriptions of current behaviour* in step with the code. Our glossary is both at once. That makes the split this: ADRs and settled vocabulary land early (Ship, or a quick Show PR), glossary entries that describe behaviour change travel with the implementing `ST-<n>` PR or are clearly marked as not yet built, and research stays off `main` or is dated as a snapshot.

## 1. Trunk-based development, DORA and Fowler

- **Two legitimate shapes.** trunkbaseddevelopment.com: developers "collaborate on code in a single branch called 'trunk'"; small teams "may commit direct to the trunk", or use "a Pull-Request workflow as long as those feature branches are short-lived and the product of a single dev-workstation". https://trunkbaseddevelopment.com/ **[V]**
- **Direct commits suit small teams that know what each other is doing.** Teams that commit straight to trunk are usually "a small team with each team member knowing what the others are up to", with a build that is "fast and relatively exhaustive". The page now also discusses agentic teams: headcount matters less than commit rate, and the safety net must be "in place before the commit rate arrives". Review doesn't vanish without a PR. It moves before the commit, after it, or into the integration step, and with agents "one agent reviews another's patch before it is queued" is one option (paraphrased in part). https://trunkbaseddevelopment.com/committing-straight-to-the-trunk/ **[V]**
- **Short-lived branches**: "the branch should only last a couple of days", one developer (or a pair) per branch, merged "after a prioritized code review". https://trunkbaseddevelopment.com/short-lived-feature-branches/ **[V]**
- **DORA**: "Have three or fewer active branches", branches that "typically last no more than a few hours", merge to trunk at least daily, no code freezes; it recommends synchronous review, because review that waits makes merges conflict more. https://dora.dev/capabilities/trunk-based-development/ **[V]**
- **Fowler, _Patterns for Managing Source Code Branches_**: CI means "you should never have more than a day's work sitting unintegrated". *Pre-Integration Review* ("Every commit to mainline is peer-reviewed before the commit is accepted") "always introduces some latency"; *integration friction* should be removed "unless it clearly adds value"; with high trust a team may prefer "post-commit review, or cutting out the reviews entirely". https://martinfowler.com/articles/branching-patterns.html **[V]**
- **Ship/Show/Ask** (Wilsenach, on Fowler's site). *Ship*: "Change goes straight on mainline", with "I updated documentation" and "I added a feature using an established pattern" as examples. *Show*: "Open a PR for feedback, but merge it straight away". *Ask*: "Open a PR for feedback and wait before merging", for "How do we feel about this new approach?". https://martinfowler.com/articles/ship-show-ask.html **[V]**
- **None of these pages treat docs differently from code**, beyond Ship/Show/Ask's documentation example. They don't discuss decision documents at all. **[V]** (checked: trunkbaseddevelopment.com's three pages, DORA and the branching-patterns article say nothing on documentation)

## 2. Docs as code

- **Write the Docs** lists issue trackers, version control and "Code Reviews" among the tools for docs, and notes "You can block merging of new features if they don't include documentation". It doesn't discuss docs-only changes landing ahead of code. https://www.writethedocs.org/guide/docs-as-code/ **[V]**
- **GitLab product docs: docs travel with the code.** "When possible, the merge request with the code should include the documentation." Work split over several MRs: MRs that build components "not yet accessible to users" need no docs, and the MR that exposes the feature does. Technical-writer review is "non-blocking", "before or after the change is merged". https://docs.gitlab.com/development/documentation/workflow/ **[V]**
- **GitLab handbook ("handbook first"): the doc change comes first, through an MR.** "A proposal is made in a merge request to the handbook. … Once merged, the change is announced." "Documenting in the handbook before taking an action may require more time initially". "The handbook is not what we hope to do … **It is what we do right now.** Make sure you change the handbook in order to truly change a process. To propose a change to a process, make a merge request". "Do not change the process first, and then view the documentation as a lower priority task." https://gitlab.com/gitlab-com/content-sites/handbook/-/blob/main/content/handbook/about/handbook-usage.md **[V]**
- **But merge quickly, and approval is optional for small changes.** "Aim to make and merge your update on the same day", so the branch doesn't fall behind and conflict. "When you expect a page owner will appreciate your changes, go ahead and merge them without approval … we practice clean up over sign off"; policy changes need code-owner approval. Same file. **[V]**
- **GitHub Docs** takes every change as a PR, deployed "within 24 hours" of merge; it doesn't say whether maintainers push directly. https://docs.github.com/en/contributing/collaborating-on-github-docs/about-contributing-to-github-docs **[V]**

What "docs-as-code" teaches here: user-facing docs describing behaviour land **with** the code that makes them true (GitLab docs), while documents that **are** the decision land **before** the action, through a fast MR (GitLab handbook). **[U]**

## 3. ADRs: before, with or after the code

- **Nygard**: statuses "proposed" and "accepted", later "deprecated" or "superseded". It doesn't say when an ADR is committed relative to code. https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions **[V]** (also in `docs/research/adrs.md`)
- **Microsoft Engineering Playbook, the only primary source found that ties status to a PR**: "ADRs can be added as pull request in the _proposed_ status to be discussed by the team until it is updated to _accepted_ to be merged with the main branch." "A proposed design can be reviewed by the development team prior to accepting it." To avoid numbering clashes when several people write ADRs in parallel, it suggests giving "ADRs the ID of the work item they relate to". https://microsoft.github.io/code-with-engineering-playbook/design/design-reviews/decision-log/ **[V]** So the ADR merges **on acceptance, ahead of the implementing code**, and the PR is the review.
- **AWS**: an owner puts the ADR in **Proposed** ("ready for review"), a team review meeting moves it to **Accepted** or **Rejected**, and it then becomes immutable. Code reviews then cite it: a reviewer who finds a violation "shares a link to the ADR", and the corrected code is "merged into the main code base". Acceptance precedes the code that conforms to it. Source control and PRs for the ADR itself aren't mentioned. https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html **[V]**
- **Azure**: "Start the ADR at the onset of a workload"; statuses "*Proposed*, *Accepted*, or *Superseded*"; "A decision that's made but never recorded will likely be forgotten". https://learn.microsoft.com/en-us/azure/well-architected/architect-role/architecture-decision-record **[V]**
- **Zimmermann, Definition of Done for an AD (ecADR)**: a decision is done when evidence, criteria, agreement and documentation are in place and its realization "has been scheduled", not built. His example decided a generator approach that "was supposed to be implemented in the next iteration". https://ozimmer.ch/practices/2020/05/22/ADDefinitionOfDone.html **[V]** He also tells reviewers to read only ADRs "marked as ready for review and ignore all draft ADRs". https://ozimmer.ch/practices/2023/04/05/ADRReview.html **[V]**
- **ThoughtWorks Radar**: store ADRs "in source control … as then they can provide a record that remains in sync with the code itself". https://www.thoughtworks.com/radar/techniques/lightweight-architecture-decision-records **[V]** ("in sync with the code" argues for the ADR not drifting ahead of the code for long. **[U]**)
- **Joel Parker Henderson**: "Commit the ADR to your git repo", with no branch guidance. Its PR section lists tools (ADR Guard, Decision Guardian) that check a PR touching watched code has an ADR, i.e. ADR **with** the code. https://github.com/joelparkerhenderson/architecture-decision-record (README at `86893bc`) **[V]**
- **MADR** and **adr.github.io** don't address when an ADR merges relative to the code. https://adr.github.io/, https://github.com/adr/madr **[V]**

Read together: the ADR sources agree a decision is recorded and **accepted before** it is implemented. The one source that names git says the acceptance point is the PR merge. None says to push an unreviewed ADR straight to `main`, and none says to hold an accepted ADR back until the code merges. **[U]**

## 4. Ubiquitous language and the glossary

- **Fowler**: the language "should be based on the Domain Model used in the software", should "evolve as the team's understanding of the domain grows". https://martinfowler.com/bliki/UbiquitousLanguage.html **[V]**
- **Evans** (_Domain-Driven Design_): "Recognize that a change in the UBIQUITOUS LANGUAGE is a change to the model." Quoted via collections of the book, not read directly. **[C]**
- **James Shore, _The Art of Agile Development_**: "The model and the ubiquitous language must always stay in sync. A change to the language implies a change to the model." "Third, update the design of the software with the change." "Delaying these changes introduces an insidious type of technical debt." https://www.jamesshore.com/v2/books/aoad1/ubiquitous_language **[V]** (Shore's book is primary for Shore; it restates Evans.)
- **None of these sources discusses a written glossary file or when it is committed.** **[V]** (checked: Fowler, Shore) The DDD position is that language and code should not stay apart for long, in either direction. Whether that means "change the glossary in the PR that renames the code" or "change the glossary first and the code soon after" isn't settled by any source. **[U]**

## 6. Multi-agent concerns, checked against this repo

- **How we land decisions now.** Of 105 first-parent commits on `main` touching `GLOSSARY.md` since 2026-10-29, 84 are not merge commits, and 58 change only `GLOSSARY.md`, `docs/adr/`, `docs/research/` or `PLAN.md`: decision-only commits pushed straight to `main`. `git log --first-parent` **[V]** No `research/*` branches exist on the remote: research notes land on `main` too. **[V]**
- **A live window where the glossary describes unbuilt behaviour.** `bcb8518` ("Record the queue pause decisions in the glossary (#693)", renaming the draft's Paused to Frozen) was pushed at 21:06Z on 2026-11-12. PR #699 (`ST-693`), which built it, was opened at 21:24Z and merged at 22:53Z. For about 1h47m `main`'s glossary said Frozen while the code said `Paused`. `gh pr view 699`; this clone's code still reads `'Paused'` in `api/src/drafts/turns.service.ts`. **[V]** The window is short when the build follows at once, and open-ended when a ticket waits behind blockers. **[U]**
- **Benefit of early landing, from the sources**: every agent's skills read only the committed glossary and ADRs (upstream domain-modeling), and parallel sessions share no context (upstream wayfinder). A decision held on an `ST-<n>` branch is invisible to the three other clones until merge, so another agent can name the same concept differently or decide the opposite. Landing on `main` closes that gap at the next pull. **[U]** (inference from **[V]** sources)
- **Cost of early landing, from the sources**: a glossary on `main` that runs ahead of code breaks the "what we do right now" property (GitLab handbook) and the "always stay in sync" property (Shore/Evans), and agents treat glossary claims as true (upstream domain-modeling). An agent working another ticket against `main` can read Frozen, find `Paused` in code, and either "fix" the code outside its ticket or call it a bug. **[U]**
- **Conflicts.** One shared `GLOSSARY.md` edited by four sessions is a hot file. Direct pushes conflict at `git pull` instead of at PR merge, so the conflict moves; it doesn't go away. Upstream's advice (agents handle conflicts; land renames first) favours landing *renames* early, which is what a vocabulary change is. **[U]**
- **Microsoft's work-item numbering** for ADRs written in parallel addresses a collision we already had: the duplicate ADR 0003 reverted in `036ef89`. **[V]**
- **No branch protection** means nothing stops a direct push today; the choice is purely a convention in the skills. **[U]**

## Implications for this repo

All inference. **[U]**

- **The two skills aren't really in conflict; they cover different artifacts.** Upstream draws the line itself: ADRs belong in the repo, research is throwaway (wayfinder branch, research FAQ). Our triage line 49 covers only `GLOSSARY.md` and `docs/adr/`, and it is a local addition, not upstream behaviour.
- **ADRs: early on `main` matches the sources, but only once *accepted*.** Our ADRs carry no status (see `docs/research/adrs.md`), so an ADR pushed during triage reads as binding immediately. Either keep pushing to `main` and treat the triage grilling with the user as the acceptance (Ship), or open a short PR and merge on acceptance (Microsoft playbook's model, a Show/Ask PR). Both agree the ADR can land before the code.
- **Glossary: split by kind of change.** A *new or renamed term* is a vocabulary decision: landing it early helps parallel agents and is upstream's "renames first". A *change to described behaviour* (Paused becomes Frozen, Cleared retired) describes code that doesn't exist yet. The sources favour either landing it with the implementing `ST-<n>` PR, or marking it as not yet built until that PR merges. Moving all glossary edits onto `ST-<n>` branches would hide decisions from the other three clones until merge, which is the problem early landing solves.
- **Research: the sources lean away from `main`.** Wayfinder's unmerged branch, or `main` with a dated "as of" title (which our notes already have), are both defensible. A stale note on `main` is what upstream's research FAQ warns against.
- **If anything changes, make it explicit in both skills**, so triage and wayfinder name the same rule for each artifact. Branch protection isn't needed to enforce a convention agents follow.
