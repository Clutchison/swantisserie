# What belongs in a CODING_STANDARDS.md for an AI reviewer (as of 2026-11-07)

What Matt Pocock's `code-review` skill expects from a repo's `CODING_STANDARDS.md`, what kind of content suits a standards file that an LLM reviewer reads, and how other review tools solve the same problem: giving an automated reviewer a repo's written standards. Written to decide whether this repo should have such a file and what would go in it.

Our `.claude/skills/code-review/` comes from `mattpocock/skills` (`skills-lock.json`: `skills/engineering/code-review/SKILL.md`). It matches upstream `main` at `4ae2317` (2026-10-31) except for one sentence that upstream added in `7739eae` (2026-10-29): "Start every sub-agent with a fresh context window." Our `retro` skill is byte-identical to upstream. Everything below cites the upstream copy.

## 1. How the `code-review` skill uses the file

- **Found by search, never required.** Step 3: "Search the repo for every file that documents how code should be written. When `CODING_STANDARDS.md` or `CONTRIBUTING.md` exists, it must be on the list." The skill names no path. Whatever the orchestrator finds goes to the Standards sub-agent as a list of files. https://github.com/mattpocock/skills/blob/main/skills/engineering/code-review/SKILL.md **[V]**
- **Why the "must" is there.** Issue #1065 (2026-09-09), "`/code-review` isn't firm enough about having to read CODING_STANDARDS.md". The orchestrator "listed standards files from memory of what I'd already read … instead of searching for them. `CODING_STANDARDS.md` sits at the repo root … and nothing in `AGENTS.md` links to it, so the sub-agent was never given the one document that would have flagged this." https://github.com/mattpocock/skills/issues/1065 **[C]** It was fixed in `3da8c01` (2026-10-07): "`code-review` now searches the repo for standards files and always hands `CODING_STANDARDS.md` / `CONTRIBUTING.md` to the Standards sub-agent". https://github.com/mattpocock/skills/blob/main/CHANGELOG.md **[V]**
- **What the reviewer is told to do with it.** "Report, per file/hunk where relevant, (a) every place the diff violates a documented standard: cite the standard (file + the rule); and (b) any baseline smell you spot … Distinguish hard violations from judgement calls: documented-standard breaches can be hard, but baseline smells are always judgement calls, and a documented repo standard overrides the baseline. Skip anything tooling enforces. Under 400 words." (SKILL.md, step 4) **[V]**
- **When there is no file.** The skill falls back on a **smell baseline**: twelve code smells from Fowler's _Refactoring_, ch. 3 (Mysterious Name, Duplicated Code, Feature Envy, Data Clumps, Primitive Obsession, Repeated Switches, Shotgun Surgery, Divergent Change, Speculative Generality, Message Chains, Middle Man, Refused Bequest). It "applies even when a repo documents nothing". Two rules bind it: "**The repo overrides.** A documented repo standard always wins; where it endorses something the baseline would flag, suppress the smell", and "**Always a judgement call.** … Like any standard here, skip anything tooling already enforces." (SKILL.md, step 3) **[V]** The docs page says: "The Standards axis needs nothing. It reads whatever the repo documents (`CODING_STANDARDS.md`, `CONTRIBUTING.md`, and the like) and falls back on a built-in baseline when the repo documents nothing." https://github.com/mattpocock/skills/blob/main/docs/engineering/code-review.md **[C]**
- **Why it reads the repo's own standards.** "This design exists to avoid a generic review skill that does not know your standards. Such a skill flags what is deliberate in your codebase and misses the invariants your codebase depends on. So the repo's own documentation is the primary source on the Standards axis, and **the repo always overrides**." (code-review docs page) **[C]**
- **Standards are kept apart from the spec.** The Spec axis checks the diff against the issue. Standards checks how it is written. The two are never merged or reranked: "A change can pass one axis and fail the other." (SKILL.md, "Why two axes") **[V]**

## 2. What Pocock says the file should contain

The guidance is in `retro`, the skill that proposes changes to the agent's environment after a session.

- **Judgement calls only. Mechanical rules become checks.** "**Coding standards**: should the **reviewer agent** be given a new rule to enforce? Should an existing rule be removed or clarified? Classify the violation first: a **mechanical** one (a fixed syntactic pattern, a banned API, an import shape, a file-location rule) gets a deterministic check, full stop: a custom rule in the repo's own linter, a new pre-commit hook, or a new CI job … Default to building the check over writing the rule. Reserve `CODING_STANDARDS.md` for genuine **judgement calls** (cross-file consistency, 'matches the surrounding style,' anything no guardrail could ever substitute for). _Use when_ the reviewer agent failed to catch a mistake." https://github.com/mattpocock/skills/blob/main/skills/engineering/retro/SKILL.md **[V]** (in the skill since it graduated to `engineering/`, `a7d038f`, 2026-09-24)
- **Why a check beats a sentence.** "A **mechanical** violation (a banned API, an import shape, a file-location rule) gets a deterministic check, because a check can fail and a sentence in a standards file can't." https://github.com/mattpocock/skills/blob/main/docs/engineering/retro.md **[C]**
- **Read by the reviewer, not the implementer.** "`CODING_STANDARDS.md`: this file is read during review, not implementation." The reason given is context pressure: "The implementation agent has the most **context pressure**. … The review agent has the least context pressure - it receives a diff, so no exploration needed. … This means that the review agent should be responsible for imposing coding standards, not the implementation agent." (retro SKILL.md, "Reference") **[V]**
- **Rules move out of CLAUDE.md into it.** A retro check category: "**Global AGENTS.md**: are there any steering instructions that should be moved to coding standards (or automated checks) instead?" (retro SKILL.md) **[V]** The docs page: "If the mistake is mechanical, the fix is a check that fails. If it is a judgement call, it goes in the coding standards the reviewer reads." (retro docs) **[C]**
- **Rules come from misses, not upfront.** "No skill ships the file. The first time a session finds a judgement-call rule for the reviewer, `retro` proposes to create it." The table row: "The reviewer missed a judgement-call mistake → A rule in `CODING_STANDARDS.md` for the reviewer agent". (retro docs) **[C]**
- **Size.** "Add **navigation pointers** to docs folders if the standards file gets more than 1,000 lines long." (retro SKILL.md) **[V]**
- **One of three levers.** An in-progress skill lists what agents need to succeed: "API's and functions which are extremely constrained and limited / Lint rules which force correctness / CODING_STANDARDS.md files which let code reviewers enforce best practices". https://github.com/mattpocock/skills/blob/main/skills/in-progress/chief-of-staff/SKILL.md **[V]** (in-progress, not shipped)

### What his own files look like

- **The template** (sandcastle's `sequential-reviewer` and `parallel-planner-with-review`, identical, and copied into `mise-en-place`) has three empty headings, Style, Testing and Architecture. The comment at the top reads: "The reviewer agent loads it during code review via @.sandcastle/CODING_STANDARDS.md so these standards are enforced during review without costing tokens during implementation." Its example bullets are generic ("Use camelCase for variables and functions", "Prefer composition over inheritance"). https://github.com/mattpocock/sandcastle/blob/main/src/templates/sequential-reviewer/CODING_STANDARDS.md **[V]**
- **Sandcastle's real file** (`.sandcastle/CODING_STANDARDS.md`, 235 lines) is nothing like the template. Most entries are a project-specific rule, then its reason, then often a BAD/GOOD code pair. Examples: "Never use `new Error()` inside an Effect closure … Raw `Error` widens the inferred error channel …", followed by a `// BAD` and a `// GOOD` block. Another: "When writing sandbox providers, don't share provider-specific code between them … The one exception is **pure, provider-agnostic utilities** … Test: if you can't tell which provider a function is for by reading it, it's a utility". Others are cross-file invariants ("Every interactive prompt in the `sandcastle init` flow must be paired with a non-interactive CLI flag … New prompt + new flag land in the same change"), platform traps that CI can't see ("This is invisible on Linux/macOS CI because both sources emit `/` there"), and review-only policy ("Reviewers enforce this; send back any PR that deletes a test without porting its cases"). https://github.com/mattpocock/sandcastle/blob/main/.sandcastle/CODING_STANDARDS.md **[V]**
- **It also documents the tooling.** About a third of the file describes the lint ratchet, the test ratchet, coverage floors and a "New-file budget" (`max-lines`: 300 …). Those are checks that already fail on their own. Code comments point back to the file (`.dependency-cruiser.mjs`: "See .sandcastle/CODING_STANDARDS.md, 'Where tests live'"). (same file) **[V]** My reading: the file doubles as the explanation of each check. That is a different job from listing judgement calls, and it sits uneasily with "skip anything tooling enforces". **[U]**
- **Sandcastle's implementer reads it too.** `.sandcastle/agent-workflows/implement/prompt.md` lists "`.sandcastle/CODING_STANDARDS.md`" with `GLOSSARY.md` and `docs/adr/` under "Read the project's domain and architecture docs before changing code". https://github.com/mattpocock/sandcastle/blob/main/.sandcastle/agent-workflows/implement/prompt.md **[V]** That contradicts the "read during review, not implementation" rule in retro and the template's comment. **[U]** (my observation)

## 3. How other tools hand a reviewer the repo's standards

| Tool | File(s) | Scoping | Severity controls | Size guidance |
| --- | --- | --- | --- | --- |
| Claude Code Review (service) | `REVIEW.md` (review only) + `CLAUDE.md` | Subdirectory `REVIEW.md`; `CLAUDE.md` in parents of changed files | Redefine Important / Nit, cap nits | 150,000 bytes |
| Claude Code `/code-review` (built-in, local) | `CLAUDE.md` only | Nested `CLAUDE.md`, `.claude/rules/` `paths` | n/a | CLAUDE.md "under 200 lines" |
| GitHub Copilot code review | `.github/copilot-instructions.md`, `.github/instructions/*.instructions.md`, `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `REVIEW.md` | `applyTo` globs; `excludeAgent` | none documented | "about 1,000 lines" per file |
| CodeRabbit | `.coderabbit.yaml` `path_instructions`; auto-detected guideline files | Glob per instruction; guideline file covers its subtree | n/a | not stated |
| Cursor Bugbot | `.cursor/BUGBOT.md` (root + nested), team rules | Nested files found by walking up from changed files | n/a | 30,000 chars per rule, 100,000 total |
| Gemini Code Assist (GitHub) | `.gemini/styleguide.md` + `.gemini/config.yaml` | `ignore_patterns` | `comment_severity_threshold` | not stated |
| Greptile | `.greptile/config.json`, `rules.md`, `files.json` | `scope` globs, cascading per directory | `severity` per rule | not stated |
| Graphite Agent (formerly Diamond) | Custom prompts in UI; file-based rules by glob | PR filters, exclusions | n/a | "Large files are truncated" |
| PR-Agent (open source) | `best_practices.md` via `repo_context_files`; `extra_instructions` | n/a | n/a | 500 lines by default |

### Anthropic: Claude Code

- **Two files with two jobs.** "**`CLAUDE.md`**: project instructions that Claude Code reads for every task, reviews included. Code Review reads them as project context and flags changes that violate them. **`REVIEW.md`**: instructions for reviews alone. Use it to say what your team wants flagged, at what severity, and what to skip." And: "Keep `REVIEW.md` to instructions that change review behavior, and leave general project context in `CLAUDE.md`." https://code.claude.com/docs/en/code-review-customize **[V]**
- **What to write, by symptom.** The page lists five symptoms, each with the kind of instruction that fixes it. The wrong things are marked Important: "redefine what 🔴 Important means for your repository". Too many nits: "cap how many 🟡 Nit comments a single review posts". Comments on generated files or "what CI already checks": "list paths and finding categories where Claude should skip findings … anything your CI already enforces like linting or spellcheck". "A team rule isn't being checked": "add rules you want flagged on every pull request, like 'new API routes must have an integration test.'" Findings that turn out to be wrong: "require evidence before a class of finding is posted … 'behavior claims need a `file:line` citation in the source, not an inference from naming'". (same page) **[V]**
- **The example `REVIEW.md`** has four sections: "What Important means here", "Cap the nits" ("Report at most five Nits per review."), "Do not report" ("Anything CI already enforces: lint, formatting, type errors"; generated files; "Test-only code that intentionally violates production rules") and "Always check" ("New API routes have an integration test", "Log lines don't include email addresses, user IDs, or request bodies", "Database queries are scoped to the caller's tenant"). (same page) **[V]**
- **Includes.** A line with only `@file.md` in the root `REVIEW.md` includes a file from the repo root. A path into a subdirectory isn't included, except `.claude/skills/<folder>/SKILL.md`. The limit is eight files and 150,000 bytes. (same page) **[V]**
- **Which branch it reads.** "Code Review reads `REVIEW.md` from the pull request's base branch or from the default branch, never from the pull request's own changes." (same page) **[V]**
- **The local `/code-review` reads less.** "The `/code-review` command … reads your `CLAUDE.md` files and not `REVIEW.md`. Put guidance you want applied in both places in `CLAUDE.md`". (same page) **[V]** By default the service "focuses on correctness: bugs that would break production, not formatting preferences or missing test coverage." https://code.claude.com/docs/en/code-review **[V]**
- **General writing rules for CLAUDE.md.** "Write instructions that are concrete enough to verify: 'Use 2-space indentation' instead of 'Format code properly'"; "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence"; "if two instructions contradict each other, Claude may pick one arbitrarily". Path-scoped rules in `.claude/rules/` with `paths:` frontmatter "only apply when Claude is working with files matching the specified patterns". https://code.claude.com/docs/en/memory **[V]**

### GitHub Copilot code review

- **Files read.** On GitHub.com, Copilot code review supports "Repository-wide instructions (using the .github/copilot-instructions.md file)", "Path-specific instructions (using .github/instructions/**/*.instructions.md files)", "Agent instructions (using AGENTS.md, CLAUDE.md, GEMINI.md or REVIEW.md files)" and "Organization instructions." https://docs.github.com/en/copilot/reference/custom-instructions-support **[V]**
- **Scoping and splitting by agent.** `applyTo` takes globs ("`src/**/*.py` - will recursively match all `.py` files in the `src` directory"). `excludeAgent` keeps a file away from either code review or the cloud agent: "Use either `"code-review"` or `"cloud-agent"`." https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions **[V]**
- **Writing advice for code review.** "Shorter instruction files are more likely to be fully processed by Copilot." Use "Distinct headings", bullet points and "Short, imperative directives". "Clear, specific instructions work better than vague directives." "Include code snippets showing both correct and incorrect patterns." "Limit any single instruction file to a maximum of about 1,000 lines." Not supported: changing comment format, the overview comment or core behaviour such as blocking merges, "Following external links" (copy the content in instead), and vague quality goals, which "add noise without improving Copilot's effectiveness, as it's already optimized to provide accurate, consistent reviews." The suggested template has sections for naming, code style, error handling, security, testing and performance. https://docs.github.com/en/copilot/tutorials/use-custom-instructions **[V]**
- **Which branch it reads.** Copilot "reads repository custom instructions, agent instructions, and agent skills from the head branch". That is the opposite of Claude Code Review. https://docs.github.com/en/copilot/concepts/prompting/response-customization **[V]**

### CodeRabbit

- **Path instructions.** In `.coderabbit.yaml` under `reviews.path_instructions`, each glob gets prose instructions, for example `src/controllers/**`: "Flag any direct database queries that bypass the ORM layer." They "work best as a targeted supplement, not a replacement", since "CodeRabbit's built-in review logic covers a wide range of issues by default." Its advice is to watch a few reviews first and add an instruction where something is consistently missed (paraphrased by the fetch tool). https://docs.coderabbit.ai/guides/review-instructions **[V]**
- **Existing guideline files are picked up automatically**: `**/AGENTS.md`, `**/.cursorrules`, `.github/copilot-instructions.md`, `.github/instructions/*.instructions.md`, `**/CLAUDE.md`, `**/.claude/rules/**/*.md`, `**/GEMINI.md`, `**/.windsurfrules`, `**/.clinerules/*` and `**/.rules/*`. Each file covers its own directory and the subtree beneath it. Other names (such as `CODING_STANDARDS.md`) have to be added as custom patterns. https://docs.coderabbit.ai/knowledge-base/code-guidelines **[V]**

### Cursor Bugbot

- "Bugbot always includes the root `.cursor/BUGBOT.md` file" plus "any additional files found while traversing upward from changed files". Order of inclusion: "Team Rules → project .cursor/BUGBOT.md (including nested files) → learned rules → manual rules." Cursor's project rules (`.cursor/rules/*.mdc`) "do not apply to Bugbot runs". Each rule is truncated at 30,000 characters, with 100,000 in total. The page's example rules are concrete checks ("Security: Flag any use of eval() or exec()"). https://cursor.com/docs/bugbot **[V]**

### Gemini Code Assist on GitHub

- `.gemini/styleguide.md` "does not have a defined schema" and "expands the standard prompt that Gemini Code Assist on GitHub uses". The docs' example is a "Company X Python Style Guide" covering line length, indentation, imports, naming, docstrings and type hints, "based on PEP 8, but with some modifications". With no style guide, review covers correctness, efficiency, maintainability, security and miscellaneous. https://docs.cloud.google.com/gemini/docs/code-review/style-guide **[V]**
- `.gemini/config.yaml` sets `comment_severity_threshold` (LOW to CRITICAL, default MEDIUM) and `ignore_patterns`. Violations of the custom style guide are said to be "typically meeting or exceeding the severity threshold". https://docs.cloud.google.com/gemini/docs/code-review/customize-repo-review **[V]**

### Greptile

- `.greptile/config.json` rules have "a `rule` string, plus optional `scope`, `severity`, and `id` fields". `rules.md` holds prose and examples: "The entire file is passed to the reviewer as context, scoped to the directory containing the `.greptile/` folder." `files.json` points at existing docs. Config cascades with per-directory overrides, and the `id` field lets a child directory disable a rule. Rules "must be specific and measurable" (example: "Functions must not exceed 50 lines"). "Follow best practices" is the bad example. "Include examples in your rule for best results." After about 10 PRs, Greptile also suggests rules from the team's patterns. https://www.greptile.com/docs/code-review/custom-standards **[V]**

### Graphite Agent (formerly Diamond)

- Custom prompts written in the UI are the recommended kind of rule. They should be "Focused": "Each rule addresses one specific concern." File-based rules point at repo docs by glob (it suggests `CONTRIBUTING.md`, `docs/architecture/*.md`). Use them "sparingly", because "Large files are truncated for performance" and "Too many files can reduce review quality". The suggested structure for writing a rule is "Rule → Bad example → Good example → Reasoning", with "2-3 clear, contrasting examples". "Try your rule on recent PRs to verify it adds value." Avoid "Non-prescriptive verbs", rules as broad as "write good code", and praise. Exclusions are a separate mechanism. https://graphite.com/docs/ai-review-customization **[V]**

### Qodo PR-Agent

- The `improve` tool loads `best_practices.md` only when it is listed in `config.repo_context_files`. That is capped by `repo_context_max_lines`, "500 lines by default". The section "Writing effective best practices files" says: "Write clearly and concisely"; "Include brief code examples when helpful with before/after patterns"; "Focus on project-specific guidelines that will result in relevant suggestions you actually want to get"; "Keep each file short and focused, since: AI models may not process effectively very long documents / Long files tend to contain generic guidelines already known to AI". It separates two kinds of instruction: `extra_instructions` steer the tool ("Don't suggest to add try-except block", "Ignore changes in toml files"), whereas "a `best_practices.md` file is a general guideline for the way code should be written in the repo." https://github.com/The-PR-Agent/pr-agent/blob/main/docs/docs/tools/improve.mdx **[V]**

### AGENTS.md

- The spec is about agents that write code, not review it. It is a "dedicated, predictable place to provide the context and instructions to help AI coding agents work on your project", with "Code style guidelines" and "Testing instructions" as popular sections. On nesting: "The closest AGENTS.md to the edited file wins". The page says nothing about code review. https://agents.md/ **[V]** Copilot and CodeRabbit both read it during review anyway (above).

### The human analogue: Google's code review guide

- "On matters of style, the style guide is the absolute authority." "Technical facts and data overrule opinions and personal preferences." "Aspects of software design are almost never a pure style issue or just a personal preference. They are based on underlying principles and should be weighed on those principles". https://google.github.io/eng-practices/review/reviewer/standard.html **[V]**
- What reviewers look for: design, functionality, complexity, "The developer isn't implementing things they might need in the future", tests, naming, comments that "mostly explain why instead of what", and "The code conforms to our style guides." A style point that the guide doesn't cover gets a "Nit:" prefix. Reviewers should not block "based only on personal style preferences". Where the guide is silent, the author should match the surrounding code (paraphrased by the fetch tool). https://google.github.io/eng-practices/review/reviewer/looking-for.html **[V]**

## 4. What suits a standards file for an LLM reviewer

### Where the sources agree

- **Project-specific rules, not generic advice.** Pocock reserves the file for "genuine judgement calls" and ships a generic baseline (Fowler) separately, so the file needn't restate it (retro, code-review). PR-Agent: "Focus on project-specific guidelines"; long files "contain generic guidelines already known to AI". Copilot: vague quality goals "add noise". Greptile: "Follow best practices" is the bad example. Graphite: not "write good code". CodeRabbit: instructions supplement built-in logic. **[V]** (sources above)
- **Leave out what tooling already enforces.** Pocock's code-review skill: "Skip anything tooling enforces". Retro: mechanical violations get "a deterministic check, full stop". Claude Code's example `REVIEW.md`: "Do not report: Anything CI already enforces". **[V]**
- **Give an example, ideally a bad/good pair.** Copilot ("both correct and incorrect patterns"), PR-Agent ("before/after patterns"), Graphite ("Rule → Bad example → Good example → Reasoning"), Greptile ("Include examples"), and Pocock's own sandcastle file (`// BAD` / `// GOOD`). **[V]**
- **Say why.** Graphite puts "Reasoning" in its rule structure. Google says design points "should be weighed on those principles". Nearly every sandcastle rule carries its reason (e.g. raw `Error` "erases the type-safe error tracking"). Pocock's `writing-for-agents` says to cache "the reason behind a choice" (see `docs/research/pruning-agent-instructions.md` §4). **[V]** A reviewer can only apply a rule to a new case, or see that an exception applies, if it knows the reason. **[U]**
- **Concrete enough to check.** Claude Code ("concrete enough to verify"), Greptile ("specific and measurable"), Copilot ("Clear, specific instructions"), Graphite ("Focused", no "Non-prescriptive verbs"). **[V]**
- **Short, or split.** Claude Code: CLAUDE.md "under 200 lines". Copilot: "about 1,000 lines" per file, and shorter "more likely to be fully processed". PR-Agent: 500-line default cap. Bugbot: 30,000 chars per rule. Graphite: large files truncated. Pocock: navigation pointers once past 1,000 lines. **[V]**
- **Add rules from observed misses.** Pocock's retro: "_Use when_ the reviewer agent failed to catch a mistake". CodeRabbit: watch reviews and add what is "consistently missed". Graphite: "Try your rule on recent PRs". Greptile: rule suggestions after about 10 PRs. **[V]**

### Recurring mechanisms that Pocock's skill lacks

- **Path scoping.** Copilot (`applyTo`), CodeRabbit (globs; subtree), Bugbot (nested files), Claude (subdirectory `REVIEW.md`, nested `CLAUDE.md`), Greptile (`scope`, cascading) and AGENTS.md (nearest file) all scope rules to paths. **[V]** Pocock's skill has no scoping: the Standards sub-agent gets every file found, plus the diff. With a single reviewer working from a diff, scoping matters less. A section heading per area ("Web specs", "API drafts") does the same job in prose. **[U]**
- **Severity.** Claude (redefine Important/Nit, cap nits), Gemini (threshold), Greptile (per-rule `severity`), Google ("Nit:"). **[V]** Pocock has two levels: documented breaches "can be hard", and baseline smells "are always judgement calls". **[V]** A standards file can say which of its rules are hard, since the skill lets documented rules be hard. **[U]**
- **Exclusions.** Claude ("Do not report"), Gemini (`ignore_patterns`), Graphite (exclusions), PR-Agent (`extra_instructions`). **[V]** Pocock's skill has none beyond "skip anything tooling enforces" and "the repo overrides". **[V]**

### Where the sources disagree

- **Who reads it.** Pocock: review only, to save the implementer's context (retro). Yet sandcastle's own implement prompt reads it. Claude Code: `CLAUDE.md` for both, `REVIEW.md` for review only. Copilot: one set of files for both, unless `excludeAgent` is set. CodeRabbit and Copilot read the implementer's files (`AGENTS.md`, `CLAUDE.md`) as review criteria. **[V]**
- **Mechanical rules.** Pocock and Claude Code exclude them. Yet Gemini's example style guide is mostly mechanical (line length, indentation, imports), Copilot's template has a "code style" section, and Greptile's model rule ("Functions must not exceed 50 lines") is one a linter could enforce. **[V]** The tools that include mechanical rules are probably filling in for repos with no linter. A repo with a linter gains nothing from repeating its rules in prose. **[U]**
- **Generic or specific.** Pocock's template's example bullets are generic ("Prefer composition over inheritance"), and his real file is specific. Copilot's template invites broad topics, while Copilot's own advice warns against vague goals. **[V]**
- **Which branch's copy applies.** Claude Code reads the base or default branch, so a PR can't loosen its own review. Copilot reads the head branch, so you can test a change to the instructions in the PR that makes it. **[V]** Pocock's skill reads the working tree at `HEAD`, which is the head branch. **[U]**
- **Standards file vs tool docs.** Retro reserves the file for judgement calls. Sandcastle's file also documents its lint ratchet, test ratchet and coverage floor. **[V]**

### A working filter for one candidate rule **[U]** (my synthesis of the above)

1. Can a linter, type, test or CI job fail on it? Build the check (retro).
2. Does the model already do it unprompted, or is it generic advice (Fowler's smells, "clear names")? Leave it out (PR-Agent, Copilot, Pocock's baseline).
3. Is it a fact about the domain (a term) or a decision (an architecture choice)? It belongs in the glossary or an ADR. The standards file can point there.
4. Otherwise it's a candidate. Write it as a rule, give the reason, add a bad/good example if the rule isn't obvious, and say whether a breach is hard.

## Implications for this repo

**What the skill will find today.** There is no `CODING_STANDARDS.md` or `CONTRIBUTING.md`. Step 3's search will therefore turn up whichever of these the orchestrator thinks of: `CLAUDE.md`, `docs/agents/web-specs.md`, `docs/agents/pick-effects.md`, `GLOSSARY.md` and `docs/adr/`. Issue #1065 is exactly that failure: a standards file that nothing points to and that the orchestrator didn't search for. **[V]** for the files; **[U]** that our runs miss them.

**What we already have, and where it belongs:**

- **Already a standards doc: `docs/agents/web-specs.md`.** "Query by role and name, assert behaviour, flush requests by URL" are judgement calls. No linter can tell a class assertion that tests layout from one that tests a state, and the file gives a reason and points to models (`harness.ts`). It also has the rule "Fix in passing … the rules are not a sweep of their own", which a reviewer needs in order to avoid flagging old specs. **[U]**
- **Partly a standard: `docs/agents/pick-effects.md`.** Mostly navigation. One paragraph is a review-time rule: "Adding a new effect of a pick means: a pure engine function with its own spec … a helper … and a restore that `undo` calls", and "a helper that writes returns what it changed". Also: a change that takes the draft row lock "gets a race there". These are cross-file invariants, retro's "cross-file consistency". **[U]**
- **Standards inside ADRs.** ADR 0012 (request bodies checked by hand-written parsers, no schema library), 0004 (shared limits live in the contract and engine) and 0007 (tournament logic lives in the engine) each imply a rule a reviewer can check against a diff. They should stay as ADRs (decision plus rationale). A standards file should point to them, not restate them (Pocock: one meaning, one source of truth). **[U]**
- **`GLOSSARY.md`.** Naming against the _Avoid_ lists is a real review check, and an LLM reviewer can do it. The glossary stays the source. A standards line can say "names in the diff use `GLOSSARY.md` terms, not those under _Avoid_". **[U]**
- **`CLAUDE.md` rules.** "New feature tests go in that feature's spec file" is a judgement call that both implementer and reviewer need. It is the kind of line retro's "Global AGENTS.md" category would move out to a standards file. That is only safe if the implementer doesn't need it upfront, so it is a judgement call to make. **[U]** "Split templates, styles and JSON fixtures before they pass 1000 lines" is mechanical. Oxlint's `max-lines: 1000` already covers TypeScript (`api/.oxlintrc.json`, `web/.oxlintrc.json`), so retro would say to extend the check to templates, styles and fixtures, not to keep it as prose. **[V]** for the configs; **[U]** for the recommendation.
- **Leave out.** Anything oxlint, `format:check`, `tsc` or CI already fails on. Generic advice the Fowler baseline covers. Commands and file locations the agent can find by looking (see `pruning-agent-instructions.md` §3).

**Smallest useful step (suggestion, not done).** A short root `CODING_STANDARDS.md` made mostly of pointers ("Web specs: `docs/agents/web-specs.md`. Pick effects: the 'Adding a new effect' rules in `docs/agents/pick-effects.md`. ADRs 0004, 0007 and 0012 bind code placement and parsing. Names follow `GLOSSARY.md`."). Then add rules only as `/retro` finds the reviewer missing them, each with its reason and a bad/good example. That makes sure the skill always finds our existing standards, without copying them. **[U]**
